#### 节点类 `RedPointTreeNode`

`export class RedPointTreeNode {     key: string;              // 节点名（如 "Mail"、"Backpack"）     val: TreeNodeData;        // observable 包装的数据（响应式！）     _independency: boolean;   // 是否独立（不受子节点影响）     _parent: RedPointTreeNode;     _children: RedPointTreeNode[]; }` 

**核心机制 —— 自底向上的值传播**：

当叶子节点的值被 `setValue()` 修改时，会自动触发父节点的 `recalculateValue()`：

`private recalculateValue(): void {     let newState = false;     let newCount = 0;     for (let c of this._children.values()) {         if (c.val.nodeState) newState = true;  // 任一子节点亮 → 父节点亮         newCount += c.val.nodeCount;            // 子节点数字累加     }     this.setValue({ nodeState: newState, nodeCount: newCount });  // 递归向上 }` 

这意味着：**只要修改叶子节点，整条路径上的祖先节点都会自动更新**。

#### 树类 `RedPointTree`

树内部维护了一个 `nodePathsMap: Map<string, RedPointTreeNode>`，用 **点分路径**（如 `"Root.Main.Mail"`）作为 key 来快速定位节点。

核心方法：

|方法|作用|
|---|---|
|`addInfoByPath(fullpath, value)`|按路径添加/更新节点，**自动创建中间缺失的节点**|
|`batchAddInfo(newInfo[], batchRefresh)`|批量更新多个节点，可选择最后统一刷新|
|`refreshTreeState()`|后序遍历整棵树，重新计算所有非叶子节点的值|
|`getNodeInfo(fullPath)`|获取节点数据，**如果节点不存在会自动创建空节点**|
|`removeChild(fullPath)`|删除整个子树分支|

`this.val = observable(new TreeNodeData());`

## 五、核心设计理念总结

### 1. 树形结构 + 自动聚合

红点天然具有层级关系（如"背包"红点 = "表情" + "光仔" + "道具"的聚合）。使用树结构后，**只需更新叶子节点，父节点自动计算**，避免了手动维护聚合逻辑。

### 2. 响应式驱动 UI（Observable Pattern）

通过 `@nx-js/observer-util` 的 `observable()` 包装节点数据，UI 层只需在 getter 中读取值，**数据变化时 UI 自动刷新**，无需手动派发事件或调用刷新方法。这是一种类似 Vue 响应式的设计。

### 3. 路径即地址（Path-based Addressing）

所有节点通过点分路径（如 `"Root.Main.Backpack.Pet.Skill"`）唯一标识，类似文件系统路径。好处：

- 直观表达层级关系
    
- 自动创建中间节点（`addInfoByPath` 会补全缺失的中间节点）
    
- 方便调试（`debug_PrintTree` 可以打印整棵树）
    

### 4. 独立节点机制（Independency）

某些节点（如服务端直接控制的 Type 节点）不应被子节点的值覆盖。通过 `changeNodeIndependency(path, true)` 设置后，该节点的 `recalculateValue()` 会跳过子节点聚合，保持服务端下发的值。

### 5. Policy 位掩码控制

通过 `TreeNodePerformPolicy.Valid` 位掩码，可以在不删除节点的情况下**临时禁用**某个红点。配合 `RedPointAdapter` 的保存/恢复机制，实现了跨场景的红点策略管理。

### 6. 数据源与消费者解耦

- **数据源**（`RedDotUniversalSourceSystem`、各业务系统）只负责调用 `contribeNewInfo()` 写入数据
    
- **消费者**（UI 组件）只负责调用 `getRedPointValue()` 读取数据
    
- 两者通过 [`RedPointSystem`](command:gongfeng.gongfeng-copilot.chat.open-symbol-in-file?%5B%7B%22%24mid%22%3A1%2C%22fsPath%22%3A%22d%3A%5C%5CCode%5C%5CTSv2%5C%5CTikiStarMain_Dev_TMR%5C%5CTikiStar%5C%5CMainBundleScripts%5C%5CMinViableSystemSet%5C%5CModules%5C%5CTikiStarPlayerInfoSystem%5C%5CUI%5C%5CTKPGPlayerInfoDetailPageSystem.ts%22%2C%22_sep%22%3A1%2C%22external%22%3A%22file%3A%2F%2F%2Fd%253A%2FCode%2FTSv2%2FTikiStarMain_Dev_TMR%2FTikiStar%2FMainBundleScripts%2FMinViableSystemSet%2FModules%2FTikiStarPlayerInfoSystem%2FUI%2FTKPGPlayerInfoDetailPageSystem.ts%22%2C%22path%22%3A%22%2Fd%3A%2FCode%2FTSv2%2FTikiStarMain_Dev_TMR%2FTikiStar%2FMainBundleScripts%2FMinViableSystemSet%2FModules%2FTikiStarPlayerInfoSystem%2FUI%2FTKPGPlayerInfoDetailPageSystem.ts%22%2C%22scheme%22%3A%22file%22%7D%2C%22RedPointSystem%22%2C%5B%7B%22line%22%3A50%2C%22character%22%3A58%7D%2C%7B%22line%22%3A50%2C%22character%22%3A72%7D%5D%5D) 这个中间层完全解耦
    

### 7. 服务端-客户端双驱动

红点数据来源有两种：

- **服务端驱动**：通过网络协议推送，经 `RedDotUniversalSourceSystem` 转换后写入树
    
- **客户端驱动**：业务系统直接调用 `contribeNewInfo()` 写入（如用户点击某项后清除红点）

### 一、整体架构

红点系统采用**服务器推送 + 客户端拉取**双模式，数据存储在客户端的**红点树（RedPointTree）**中，UI 组件通过绑定树节点路径来响应红点状态变化。

### 二、推送触发时机

后台在以下时机会推送红点通知（`E_SVR_MSG_ID_RED_POINT_NOTIFY_RED_LIST`，msgId=6400）：

|触发时机|说明|
|---|---|
|**玩家登录**|登录后服务器主动下发全量红点列表|
|**状态变更**|玩家获得新物品/称号/头像/动作等时，服务器推送增量红点|
|**客户端主动拉取**|客户端调用 `reqGetRedPointList`（msgId=6401）请求，服务器返回后触发同样的处理流程|
|**断线重连**|`RedDotUniversalSourceSystem.onReconnectSuccess` 中主动拉取|

|**客户端请求清除**|用户点击/查看了某个物品|`E_SVR_MSG_ID_USER_INFO_CLEAR_RED_DOT`（msgId=9017），参数为 `vecItemId`|
|**服务器推送更新**|服务器状态变更后重新推送|推送中 `iLightOff = 0` 的子节点会被设为 false|
|**增量差异清除**|新推送中未提及的已有节点|`childrenToCheck` 中剩余的节点被设为 false|

#### 5.1 增量差异清除的关键逻辑

`// contribeToRedpointTree 中的关键逻辑 let childrenToCheck = this.getAllNodeInChildrenTree(RedPointConfig.path);  newInfo.vecRedSubList.forEach((RedSubItem) => {     // ... 构建路径 ...     childrenToCheck = childrenToCheck.filter((value) => { return value !== Itempath });     RedPointInfos.push({ path: Itempath, Info: { nodeState: RedSubItem.stData.iLightOff > 0, ... } }); });  // 服务器推送中没有提到的节点 → 设为 false childrenToCheck.forEach((value) => {     RedPointInfos.push({ path: value, Info: { nodeState: false, nodeCount: 0 } }); });` 

这意味着：**每次服务器推送某个类型的红点时，是全量覆盖该类型下的所有子节点**。推送中提到的节点按 `iLightOff` 设置状态，未提到的节点全部清零。

### 六、总结：后台推送的核心机制

1. **推送模式**：服务器通过 `E_SVR_MSG_ID_RED_POINT_NOTIFY_RED_LIST` 消息主动推送红点数据，按 `E_RED_POINT_TYPE` 分类
    
2. **数据粒度**：每个类型下有 `vecRedSubList` 列表，包含具体物品ID和其红点状态
    
3. **全量语义**：客户端将推送视为该类型的**全量快照**——推送中有的按状态设置，推送中没有的清零
    
4. **树形冒泡**：叶子节点状态变化后，自动向上冒泡到所有祖先节点
    
5. **清除请求**：用户查看物品后，客户端发送 `E_SVR_MSG_ID_USER_INFO_CLEAR_RED_DOT` 通知服务器清除对应物品的红点状态
    

**之前 bug 的根因**就在于：服务器在赛季切换回收称号后，推送的 `vecRedSubList` 中仍然包含了已回收称号的 `iLightOff > 0` 数据，客户端忠实地将其写入红点树，导致异常红点显示。
